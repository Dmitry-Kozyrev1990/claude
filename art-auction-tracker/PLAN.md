# Трекер аукционных цен на искусство: план реализации

Документ описывает, как собрать проект из исходной концепции: сбор данных → нормализация и
сопоставление → хранение и аналитика → интерфейс и уведомления. Сначала идут поправки к концепции,
потом архитектура, модель данных, алгоритмы, стек и дорожная карта.

---

## 0. Что стоит поправить в концепции до старта

1. **Начинать с узкой ниши, а не со «всего арт-рынка».** Уникальные картины перепродаются редко
   (раз в 10–30 лет), поэтому «таймлайн предмета» для них почти пуст. Тиражная графика и эдиции
   (офорты Рембрандта, литографии Пикассо, шелкографии Уорхола, принты Бэнкси) продаются
   сотнями раз в год, у них есть номера в каталогах-резоне (Bartsch, Feldman-Schellmann и т. п.),
   и на них сразу видна динамика. Лучший MVP — 20–50 авторов тиражной графики.
2. **Пример с «The Three Crosses, State IV» — не дубль, а разные объекты.** У гравюр состояния
   (states) — разные версии доски, и State I может стоить в разы дороже State IV. Поэтому модель
   данных нужна многоуровневая: *Произведение → Вариант/Состояние → Физический экземпляр → Продажа*.
   Сопоставление должно привязывать лот к произведению и отдельно извлекать состояние и номер оттиска.
3. **Обход Cloudflare/Kasada капча-солверами — не стоит закладывать в коммерческий продукт.**
   Это прямое нарушение ToS, а в ЕС базы данных дополнительно защищены правом *sui generis*.
   Реалистичнее: публичные страницы без обхода защиты, вежливый темп запросов, лицензирование
   данных (Artnet, MutualArt, Artprice продают доступ), партнёрства с региональными домами,
   которым выгодна видимость. Перед запуском — консультация юриста по целевой юрисдикции.
4. **Изображения и тексты каталогов защищены авторским правом.** Цены и даты — факты, их хранить
   можно спокойнее. Изображения храните для внутреннего анализа (эмбеддинги, миниатюры), а
   пользователю показывайте ссылку на источник.
5. **Elasticsearch на старте не нужен.** PostgreSQL + `pg_trgm` + полнотекстовый поиск закрывают
   поиск по авторам и названиям до миллионов лотов. ES/OpenSearch — во второй фазе.

## 1. Общая архитектура

```
 ┌─────────────┐   ┌──────────────┐   ┌──────────────┐   ┌───────────────┐
 │ Планировщик │──▶│  Краулеры    │──▶│ Сырое храни- │──▶│  Парсеры /    │
 │ (Prefect /  │   │ Scrapy +     │   │ лище (S3/    │   │  экстракторы  │
 │  Airflow)   │   │ Playwright   │   │ MinIO): HTML,│   │  → RawLot     │
 └─────────────┘   └──────────────┘   │ JSON, фото   │   └───────┬───────┘
                                      └──────────────┘           │
                                                                 ▼
 ┌──────────────┐   ┌───────────────────────┐   ┌─────────────────────────┐
 │ Аналитика    │◀──│ PostgreSQL (+pgvector │◀──│ Нормализация + Entity   │
 │ dbt-витрины: │   │ +TimescaleDB)         │   │ Resolution (NLP + CV),  │
 │ индексы,     │   │ артисты, работы, лоты │   │ очередь ручной проверки │
 │ CAGR, BIAS   │   └───────────┬───────────┘   └─────────────────────────┘
 └──────┬───────┘               │
        ▼                       ▼
 ┌──────────────┐   ┌───────────────────────┐   ┌─────────────────────────┐
 │ FastAPI      │──▶│ Веб (Next.js), B2B API│   │ Движок алертов →        │
 │ REST/GraphQL │   │ дашборды, watchlist   │   │ Telegram / Email        │
 └──────────────┘   └───────────────────────┘   └─────────────────────────┘
```

Ключевой принцип: **сбор, парсинг и нормализация — отдельные шаги.** Сырые ответы сохраняются
навсегда, поэтому при поломке или улучшении парсера всю историю можно перепарсить без повторного
скачивания.

## 2. Этап 1 — Сбор данных

### Источники по приоритету

| Группа | Примеры | Комментарий |
|---|---|---|
| Агрегаторы-площадки | Invaluable, LiveAuctioneers, the-saleroom, Drouot, Lot-tissimo | Одна интеграция = сотни мелких домов |
| Крупные дома | Christie's, Sotheby's, Phillips, Bonhams | Самые дорогие лоты, сильнейшая защита |
| Региональные дома | Heritage, Dorotheum, Lempertz, Ketterer, Artcurial; в РФ — Vladey, Совком, «Литфонд», MacDougall's | Часто проще технически и открыты к партнёрству |
| Справочники | Getty ULAN (авторы), Getty AAT (техники), Wikidata | Канонические ID для нормализации, открытые |
| Курсы валют | ECB, ЦБ РФ | Пересчёт цен на дату торгов |

### Как устроен краулинг

1. **Календарь торгов.** Ежедневно обходить страницы с расписанием аукционов → таблица `sales`.
2. **Каталог лотов.** Для каждого предстоящего аукциона скачать все лоты (заранее, до торгов:
   эстимейты, описание, фото).
3. **Повторные обходы после торгов по расписанию: T+0 (сразу), T+1, T+7, T+30.** Так ловится
   Price realized, пока страница не удалена или не скрыта за логином, и фиксируются продажи после торгов.
4. **Технически:** Scrapy для статичных страниц; Playwright только там, где без JS никак.
   Многие сайты подгружают лоты из внутреннего JSON — его парсить надёжнее, чем HTML
   (но проверьте ToS). Ограничение темпа (`AUTOTHROTTLE`), кэш, ротация User-Agent, уважение
   `robots.txt`.
5. **Сырые данные** → S3/MinIO с ключом `source/date/url_hash` + метаданные (время, HTTP-статус).

### Единая схема «сырого лота» (выход парсера)

```python
class RawLot(BaseModel):
    source: str                 # "christies"
    source_lot_id: str          # уникальный id лота на сайте
    sale_id: str
    lot_number: str             # "112A" — номера бывают не числовыми
    url: HttpUrl
    artist_raw: str | None      # "Attributed to Rembrandt Harmensz. van Rijn"
    title_raw: str | None
    date_raw: str | None        # "circa 1653-55"
    medium_raw: str | None      # "drypoint and burin on laid paper"
    dimensions_raw: str | None  # "38.5 x 45 cm (15 1/8 x 17 3/4 in.)"
    estimate_low: Decimal | None
    estimate_high: Decimal | None
    currency: str
    price_realized: Decimal | None
    price_includes_premium: bool | None
    status: Literal["upcoming", "sold", "bought_in", "withdrawn", "unknown"]
    description_raw: str | None  # провенанс, литература, примечания
    image_urls: list[HttpUrl]
    fetched_at: datetime
    raw_document_key: str       # ссылка на сырой HTML/JSON в S3
```

### Мониторинг поломок парсеров

Парсеры будут ломаться — нужно узнавать об этом за часы, а не за месяцы. Для каждого источника
считать долю заполненности полей (`price_realized`, `estimate`, `artist`) и число лотов на аукцион.
Резкое падение (например, `price_realized` заполнено у 0 % проданных лотов) → алерт в Telegram.
Плюс фикстуры: сохранённые HTML-страницы и тесты парсеров на них.

**LLM как резервный экстрактор.** Когда вёрстка меняется, LLM со structured output (JSON по схеме
`RawLot`) достаёт поля из текста страницы. Дорого для массового потока, но отлично как запасной путь
и для разметки «грязных» полей (`date_raw`, `medium_raw`).

## 3. Этап 2 — Нормализация и сопоставление (Entity Resolution)

### 3.1 Нормализация полей

| Поле | Что делать |
|---|---|
| Автор | Отделить **квалификатор атрибуции** (`Attributed to`, `Circle of`, `Studio of`, `School of`, `After`, `Manner of`) — он меняет цену в разы и должен быть отдельным полем. Имя сопоставить со справочником алиасов → ULAN/Wikidata ID |
| Дата | `circa 1653`, `1653-55`, `executed in the 1960s` → `year_from`, `year_to`, `is_circa` |
| Размеры | Регулярки + единицы → `height_cm`, `width_cm`, `depth_cm`; различать размер листа и изображения |
| Техника | Привести к таксономии (Getty AAT): `oil on canvas` → живопись/масло; `etching, drypoint` → печатная графика |
| Цена | Пересчёт в USD/EUR по курсу на дату торгов; привести к единому виду **с премией покупателя или без** (у каждого дома своя шкала премии, и она менялась по годам). Отдельно — цены с поправкой на инфляцию (CPI) |
| Эдиция | `numbered 23/50`, `artist's proof`, `State IV`, номер в каталоге-резоне (`Bartsch 78`, `B. 78`, `F&S II.31`) → отдельные поля |

### 3.2 Модель «что считать одним и тем же»

- **Artist** — человек (с алиасами).
- **Work** — произведение (композиция): «Три креста» Рембрандта.
- **Variant** — состояние/тираж: State IV, эдиция 50 экз.
- **Object** — физический экземпляр (конкретный оттиск или холст).
- **Lot/Sale event** — появление объекта на торгах.

Повторная продажа одного **Object** даёт чистую точку для CAGR. Продажи разных экземпляров одной
**Variant** дают ценовую историю эдиции.

### 3.3 Конвейер сопоставления

1. **Блокировка (blocking)** — не сравнивать всё со всем. Кандидаты: тот же `artist_id` + тот же
   класс техники + размеры в пределах ±5 % (или совпавший номер каталога-резоне).
2. **Признаки для каждой пары:**
   - текст: схожесть названий (нормализация, Jaro-Winkler, мультиязычные эмбеддинги вроде
     `multilingual-e5` / LaBSE — названия бывают на английском, французском, немецком);
   - числа: разница размеров, годов;
   - точные ключи: совпадение номера в каталоге-резоне, номера оттиска;
   - изображение: косинусная близость эмбеддингов CLIP / DINOv2; перцептивный хэш (pHash) для
     точных копий одной фотографии; для финальной проверки — сопоставление локальных признаков
     (SIFT/ORB, LoFTR), которое отличает два оттиска одной гравюры от одного и того же оттиска;
   - провенанс: пересечение имён прежних владельцев и выставок в описании.
3. **Классификатор пар** (логистическая регрессия / LightGBM) на размеченных вручную парах. Без
   разметки можно начать с вероятностной модели Fellegi–Sunter — готовая реализация есть в
   библиотеке **Splink**.
4. **Кластеризация**: связные компоненты по рёбрам с вероятностью выше порога и с ограничениями
   (два лота из одного аукциона не могут быть одним объектом).
5. **Human-in-the-loop**: пары в «серой зоне» (например, 0.6–0.9) попадают в очередь проверки к
   арт-эксперту; его решения становятся новой обучающей выборкой.

Поиск похожих изображений: эмбеддинги в `pgvector` (или Qdrant/FAISS при больших объёмах),
ANN-поиск top-K соседей → эти соседи тоже становятся кандидатами в пары.

## 4. Этап 3 — Хранение и аналитика

### 4.1 Основные таблицы PostgreSQL

```sql
artists        (id, canonical_name, ulan_id, wikidata_id, birth_year, death_year, nationality)
artist_aliases (artist_id, alias, lang)
works          (id, artist_id, title_canonical, year_from, year_to, medium_class,
                height_cm, width_cm, catalogue_ref, is_multiple)
variants       (id, work_id, state, edition_size)
objects        (id, variant_id, impression_number, notes)
auction_houses (id, name, country)
sales          (id, house_id, source_sale_id, title, city, starts_at, ends_at, currency)
lots           (id, sale_id, source_lot_id, lot_number, attribution_qualifier,
                title_raw, est_low, est_high, currency, hammer_price, premium_price,
                price_usd, status, url, raw_document_key)
lot_images     (lot_id, s3_key, phash, embedding vector(768))
lot_links      (lot_id, object_id, confidence, method, reviewed_by, reviewed_at)
users, watchlists, saved_searches, alerts, notification_log, api_keys, subscriptions
```

### 4.2 Метрики

| Метрика | Расчёт | Подводный камень |
|---|---|---|
| **CAGR объекта** | `(P2 / P1) ** (1 / лет) - 1` по повторным продажам одного Object | Смещение отбора: перепродают в основном удачные покупки |
| **Индекс автора / направления** | Repeat-sales (метод Mei Moses / Case-Shiller) там, где хватает повторов; иначе **гедонистическая регрессия**: `log(price) ~ размер + техника + год создания + дом + город + атрибуция + фиктивные переменные периода` — коэффициенты периодов и есть индекс | Мало сделок у малоизвестных авторов → доверительные интервалы показывать обязательно |
| **Ликвидность автора** | Доля проданных (sell-through rate), число лотов в год, число домов/стран, медианный срок между перепродажами | Снятые лоты (withdrawn) не считать как непроданные |
| **BIAS к эстимейту** | Доли лотов: выше верхней оценки / внутри / ниже нижней; средний `price / mid_estimate` | Сравнивать цену и эстимейт в одной базе (эстимейт обычно без премии) |
| **Справедливая стоимость** | Модель (LightGBM с квантильной регрессией) → диапазон P10–P90 для работы пользователя | Это оценка, не экспертиза; юридически так и формулировать |

Расчёт — ночным пакетом: **dbt** собирает витрины (`mart_artist_index`, `mart_artist_liquidity`,
`mart_estimate_bias`), API отдаёт уже готовые цифры.

## 5. Этап 4 — Интерфейс и уведомления

- **Веб-приложение** (Next.js + графики на ECharts/Recharts): поиск, страница автора (индекс, объём
  продаж, BIAS, ликвидность), страница работы (таймлайн продаж), страница аукциона.
- **Личный кабинет**: Watchlist (авторы, работы, сохранённые поиски), «Моя коллекция» с
  загрузкой фото своей работы и оценкой справедливой стоимости.
- **Движок алертов**: при загрузке нового предстоящего лота он проверяется по правилам
  пользователей (автор + техника + диапазон эстимейта) и по визуальной близости к фото из «Моей
  коллекции» (kNN по эмбеддингам). Дедупликация, чтобы не слать одно и то же дважды.
- **Каналы**: Telegram-бот (aiogram), email (Postmark / Amazon SES / SendGrid), дайджест раз в
  день или мгновенно — на выбор пользователя.
- Пример сообщения: «Работа Х, похожая на вашу (сходство 0.91), выставлена на Bonhams,
  лот 145, 12 ноября, эстимейт $40 000–60 000. Медианная цена похожих работ за 3 года: $52 000».

Для внутренней аналитики на старте вместо своего фронтенда достаточно Metabase или Streamlit.

## 6. Технологический стек (уточнённый)

| Слой | MVP | Рост |
|---|---|---|
| Краулинг | Scrapy + scrapy-playwright | + Zyte API/свои прокси при лицензированном доступе |
| Оркестрация | Prefect или cron + Celery | Airflow / Dagster |
| Сырые данные | MinIO / S3 | то же |
| БД | PostgreSQL 16 + pg_trgm + pgvector | + TimescaleDB, OpenSearch, Qdrant |
| ER / NLP | rapidfuzz, Splink, sentence-transformers | свой классификатор пар + разметочный интерфейс (Label Studio) |
| CV | open_clip (CLIP ViT-B/32) или DINOv2, imagehash | дообученная модель на парах «тот же / другой объект» |
| Аналитика | pandas, statsmodels, LightGBM, dbt | то же |
| Бэкенд | FastAPI, SQLAlchemy, Redis, Celery/Arq | + GraphQL, лимиты для B2B API |
| Фронтенд | Next.js, ECharts | то же |
| Оплата | Stripe / ЮKassa | + счета для B2B |
| Инфраструктура | Docker Compose на 1–2 VPS, managed Postgres | Kubernetes, отдельный GPU-воркер для эмбеддингов |
| Наблюдаемость | Sentry, Grafana + Prometheus | то же |

### Структура репозитория

```
art-tracker/
  crawlers/           # Scrapy-проект: один spider на источник
  parsers/            # сырой HTML/JSON → RawLot, тесты на сохранённых страницах
  normalize/          # авторы, даты, размеры, техники, валюты
  matching/           # blocking, признаки, классификатор, кластеризация
  vision/             # эмбеддинги изображений, pHash
  analytics/          # dbt-проект + Python-модели (индексы, оценка стоимости)
  api/                # FastAPI
  web/                # Next.js
  alerts/             # движок правил + Telegram/Email
  flows/              # Prefect-флоу: расписание обходов и пересчётов
  infra/              # docker-compose, миграции (Alembic)
```

## 7. Дорожная карта

| Фаза | Срок | Результат |
|---|---|---|
| **0. Подготовка** | 2–3 недели | Консультация юриста, выбор ниши (например, тиражная графика 30 авторов), список 5–10 источников с оценкой доступа, схема БД |
| **1. MVP данных** | 1–2 месяца | 3–5 источников, сырое хранилище, парсеры с тестами, нормализация авторов/цен/размеров, сопоставление по правилам (автор + каталог-резоне + размеры), Metabase для себя |
| **2. MVP продукта** | +1–2 месяца | Сайт: поиск, страницы авторов и работ, графики; Watchlist + Telegram-алерты; первые 20–50 пользователей бесплатно для обратной связи |
| **3. ML-сопоставление** | +2–3 месяца | Эмбеддинги изображений, классификатор пар, очередь ручной проверки, индексы (repeat-sales + гедонистический) |
| **4. Монетизация** | параллельно с 3 | Платная подписка, оценка «справедливой стоимости», затем B2B API и квартальные отчёты |
| **5. Масштаб** | дальше | Новые сегменты (живопись, фото, дизайн), лицензированные данные, OpenSearch, мультиязычный интерфейс |

### Команда

- MVP может сделать один сильный разработчик на Python за 3–4 месяца, если ниша узкая.
- Полноценный продукт: data-инженер (краулеры и пайплайн), ML/DS (сопоставление, индексы, оценка),
  fullstack (API и фронтенд), арт-эксперт на частичной занятости (разметка, атрибуции, контент
  отчётов), юрист на консультациях.

### Ориентир по ежемесячным расходам на старте

Серверы и managed Postgres — $100–300, S3 — $10–50, почтовый сервис — $0–50, GPU для пакетного
расчёта эмбеддингов — по требованию, $20–100. Лицензированные данные — от сотен до тысяч долларов в
месяц, это главная статья расходов при легальном масштабировании.

## 8. Монетизация: что учесть при реализации

- **B2C-подписка**: бесплатный уровень (поиск, последние продажи с задержкой) → платный (история,
  индексы, алерты, оценка своей коллекции). Ценность для коллекционера — алерты и «справедливая цена».
- **B2B (банки, страховые, галереи)**: им нужны API, SLA, объяснимость оценки (какие аналоги и
  поправки дали цифру) и аудит-лог. Объяснимость закладывайте в модель с самого начала: хранить
  аналоги, на которых основана оценка.
- **Отчёты**: автоматическая генерация из dbt-витрин (топ растущих авторов, sell-through по домам,
  BIAS по сегментам) + редакторский текст.

## 9. Главные риски и что с ними делать

| Риск | Мера |
|---|---|
| Юридические претензии | Юрист до запуска; лицензирование и партнёрства; не публиковать чужие изображения и тексты; не обходить технические средства защиты |
| Поломки парсеров | Сырое хранилище + перепарсинг, тесты на фикстурах, алерты на заполненность полей, LLM-экстрактор как запасной путь |
| Скрытые и удаляемые цены | Обход сразу после торгов (T+0/T+1), архив сырых страниц |
| Ошибки сопоставления | Порог уверенности, ручная проверка серой зоны, показ уверенности в интерфейсе, возможность пользователю сообщить об ошибке |
| Мало данных для индексов | Узкая ниша с частыми продажами, доверительные интервалы, гедонистическая модель вместо чистого repeat-sales |
| Несопоставимость цен | Единая база (с премией или без), пересчёт валют на дату торгов, флаг «цена неизвестна» вместо нуля |
